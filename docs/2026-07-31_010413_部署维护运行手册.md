# MahoShojo Generator 部署维护运行手册

> 记录时间：2026-07-31  
> 适用范围：当前 Next.js 15 + OpenNext Cloudflare + Cloudflare D1 + Better Auth + Tailwind 4 项目。  
> 目标：把近期部署、认证、数据库、AI 供应商、管理员与公开战报功能中踩过的坑整理成可执行维护文档。  
> 安全说明：本文只记录变量名、流程和排错方法，不记录任何真实 API Key、Token、Secret 或 .env.local 内容。

## 1. 项目定位与关键目录

本项目使用 App Router 作为统一路由体系：

| 范围 | 位置 | 说明 |
| --- | --- | --- |
| 页面 | `app/**/page.tsx` | 例如 `/arena`、`/arena-reports`、`/admin` |
| API | `app/api/**/route.ts` + `handler.ts` | API 入口与业务处理拆分 |
| 组件 | `components/` | 公开战报、个人中心、管理员页等 UI |
| AI 配置 | `lib/ai/*`、`lib/config.ts`、`config/*` | 供应商、模型、冷却、生成参数 |
| 数据库 schema | `lib/db/schema/business.ts`、`lib/database/schema.sql` | Drizzle schema 与目标 SQL |
| 仓储层 | `lib/db/repositories/*` | 新功能应优先走仓储层，不要在 API 里散写 SQL |
| 数据库封装 | `lib/database/*` | 给业务层调用的兼容封装 |
| 迁移 | `drizzle/*.sql` | 线上 D1 需要实际执行，不会只因代码变更自动生效 |
| 文档 | `docs/` | 正式维护说明放这里 |

## 2. 本地环境基线

### Node 与 pnpm

项目固定包管理器：

```powershell
pnpm --version
```

应使用 `pnpm@11.3.0`。如果本机 Node 版本不合适，可以用 nvm 切换：

```powershell
nvm list
nvm install <node_version>
nvm use <node_version>
```

注意事项：

- 不要用旧版 pnpm 安装依赖，旧 pnpm 可能改写当前 v9 lockfile。
- 如果 Corepack 出现 `Cannot find matching keyid`，这是本机包管理环境问题，不代表项目构建失败。
- 常规安装使用：

```powershell
pnpm install
```

## 3. 环境变量配置

从 `env.example` 复制到 `.env.local`：

```powershell
Copy-Item env.example .env.local
```

关键变量分类如下。

### AI 供应商

| 变量 | 作用 | 维护要点 |
| --- | --- | --- |
| `AI_PROVIDERS_CONFIG` | 服务端默认 AI 供应商配置 | 共享 Key 放服务端，不要放前端 |
| `AI_LOAD_BALANCE_STRATEGY` | 供应商负载策略 | 当前可按配置决定优先级/随机 |
| `NEXT_PUBLIC_AI_SAFETY_PROMPT_LEVEL` | 前端安全提示等级 | 前端可见，只放非敏感配置 |
| `NEXT_PUBLIC_ENABLE_BUNDLE_SAFETY_CHECK` | 打包/导入内容安全检查开关 | 修改后需重启服务 |

维护原则：

- 服务端默认供应商和前端 BYOK 可选模型是两套配置。
- 服务端共享 API Key 不应写入 `NEXT_PUBLIC_*`。
- 自定义供应商模型列表必须按实际可用模型维护，避免 UI 里列出不可用模型。

### Cloudflare D1

| 变量 | 作用 |
| --- | --- |
| `CLOUDFLARE_API_TOKEN` | 本地/脚本通过 Cloudflare API 访问 D1 |
| `CLOUDFLARE_ACCOUNT_ID` | Cloudflare 账号 ID |
| `D1_DATABASE_ID` | D1 数据库 ID |

常见坑：

如果看到类似：

```text
Could not route to /client/v4/accounts/your_cloudflare_account_id_here/d1/database/your_d1_database_id_here/raw
```

说明环境变量还是占位符，或者账号 ID / 数据库 ID 不匹配。检查 `.env.local` 里的三个变量，不要把 `your_cloudflare_account_id_here`、`your_d1_database_id_here` 这类占位符留在线上或本地生产启动环境中。

### R2

| 变量 | 作用 |
| --- | --- |
| `R2_*` 系列 | 战报正文等大对象存储 |
| `CLOUDFLARE_R2_*` 系列 | 通过 Cloudflare API/S3 兼容接口操作 R2 |

未配置 R2 时，部分逻辑会回退到 D1 预览或摘要，但大体积战报长期建议走 R2。

### 登录、注册、邮箱

| 变量 | 作用 |
| --- | --- |
| `BETTER_AUTH_SECRET` | Better Auth 密钥，必须长且随机 |
| `BETTER_AUTH_URL` | 站点主 URL |
| `BETTER_AUTH_TRUSTED_ORIGINS` | 允许的登录/注册来源 |
| `RESEND_API_KEY` | Resend 邮件发送 Key |
| `NEXT_PUBLIC_TURNSTILE_SITE_KEY` | Turnstile 前端 Site Key |

常见坑：

- 公网或局域网访问时，如果后端报 `Invalid origin: http://10.x.x.x:3000`，需要把这个访问地址加入 `BETTER_AUTH_TRUSTED_ORIGINS`。
- `BETTER_AUTH_URL` 应与实际访问入口一致；如果多入口访问，至少 trusted origins 要覆盖。
- Resend 需要域名验证。没有域名时，可以先关闭强邮箱验证或只本地测试账号系统。
- 不要把 Resend Key 或 Better Auth Secret 写入前端变量。

### 安全头与 HTTP/LAN 部署

| 变量 | 作用 |
| --- | --- |
| `MAHOSHOJO_ENABLE_HTTPS_SECURITY_HEADERS` | 是否启用强 HTTPS 安全头 |
| `NEXT_PUBLIC_GA_ID` | Google Analytics，可选 |

局域网 HTTP 部署踩过的坑：

- 私有/虚拟 LAN 地址需要被浏览器安全头逻辑识别，否则可能出现 CSS 不加载、页面只有白底文字、请求被浏览器拦截。
- 当前逻辑已支持常见 RFC1918、link-local、CGNAT、以及虚拟 LAN 段，包括 `25.x.x.x` / `26.x.x.x`。
- 公网 HTTP 不建议长期使用，最好配置 HTTPS。

## 4. Cloudflare D1 初始化与迁移

### 首次初始化

新 D1 不能只跑后续 migration。应先应用完整基础 schema：

```powershell
# 示例：具体 database 名称以 wrangler.jsonc 为准
pnpm exec wrangler d1 execute <database_name> --remote --file lib/database/schema.sql
```

原因：后续 drizzle migration 往往依赖已有基础表。空库直接跑局部 ALTER 可能失败。

### 日常迁移

项目已有脚本：

```powershell
pnpm run db:migrate:remote:prod
pnpm run db:status:remote:prod
pnpm run db:status:remote:prod:ready
```

维护注意：

- `lib/database/schema.sql` 是目标结构，不等于线上已经执行。
- 每次新增字段都要同步：
  - `lib/db/schema/business.ts`
  - `lib/database/schema.sql`
  - `drizzle/*.sql`
  - repository 类型和 mapper
  - API DTO / 前端类型
  - 相关测试

### 最近新增过的战报字段/表

| 迁移 | 作用 |
| --- | --- |
| `drizzle/0015_public_battle_reports.sql` | 公开战报相关字段 |
| `drizzle/0016_battle_report_notes.sql` | `battle_report_generations.note` 公开备注 |

如果线上出现“代码读写 note 但数据库无列”，执行：

```sql
ALTER TABLE battle_report_generations ADD COLUMN note TEXT;
```

执行前建议先查表结构，避免重复添加。

### `.next/prerender-manifest.json` 缺失

报错：

```text
ENOENT: no such file or directory, open '.next/prerender-manifest.json'
```

原因：

- `.next` 是半成品。
- 上一次 `next build` 被中断、超时或没有完整完成。
- 直接 `next start` 但没有完整生产构建。

处理：

```powershell
pnpm exec next build
pnpm next start
```

确认文件：

```powershell
Test-Path .next/prerender-manifest.json
```

### `Could not find a production build in the '.next' directory`

原因：没构建或构建目录被清理。

处理：

```powershell
pnpm exec next build
pnpm next start
```

### OpenNext ESM warning

常见警告：

```text
CommonJS module next.config.compiled.js is loading ES Module @opennextjs/cloudflare...
```

这是 Node 对 CJS/ESM 混用的实验性警告。只要构建/启动成功，通常可忽略。

## 6. 登录注册系统维护

### 当前状态

系统存在：

- 旧账号兼容登录/注册接口
- Better Auth 集成
- 用户表 `users`
- 管理员字段 `users.is_admin`
- 审核豁免字段 `users.is_review_exempt`
- 角色卡容量字段 `users.slot_count`

### Origin 相关错误

报错：

```text
Better Auth: Invalid origin: http://10.126.126.1:3000
```

处理：

1. 把实际访问地址加入 `BETTER_AUTH_TRUSTED_ORIGINS`。
2. 确认 `BETTER_AUTH_URL` 与主访问地址匹配。
3. 重启服务。
4. 如果同时支持 `localhost`、LAN IP、公网 IP，都要列入 trusted origins。

### “网络错误：Cannot read properties of undefined (reading 'digest')”

这个错误曾出现在登录/注册链路。排查顺序：

1. 浏览器 Network 看实际失败接口。
2. 后端日志确认是否进入 `app/api/auth/*`。
3. 检查 D1 环境变量是否仍是占位符。
4. 检查 Better Auth 配置是否缺少 secret/url/origin。
5. 检查构建产物是否为最新。

### 去除登录缓冲/注册安全验证

当前曾调整过登录/注册相关限流与安全验证。维护原则：

- 修改安全策略要保留服务端校验，不只改前端。
- 如果关闭 Turnstile 或邮箱验证，应清楚知道这会降低抗滥用能力。
- 管理员操作仍必须保留服务端权限校验。

## 7. 管理员与用户状态管理

### 管理员页面

已新增管理员后台：

| 路径 | 作用 |
| --- | --- |
| `/admin` | 管理员工作台 |
| `/api/admin/users` | 用户管理 |
| `/api/admin/data-cards` | 卡片管理 |
| `/api/admin/battle-reports` | 战报管理 |
| `/api/admin/settings` | 站点配置 |

安全措施：

- 服务端读取当前用户并检查 `is_admin`。
- mutation 请求检查 same-origin。
- 防止自我降权/自封禁。
- 防止移除最后一个管理员。
- 管理操作写审计日志。

### 给用户添加管理员

安全操作建议：

1. 同时核对用户 ID 和用户名。
2. 更新前读一次。
3. 条件更新时同时匹配 ID 和用户名。
4. 更新后读回确认。

示例 SQL：

```sql
SELECT id, username, is_admin FROM users WHERE id = ? AND username = ?;
UPDATE users SET is_admin = 1, updated_at = CURRENT_TIMESTAMP WHERE id = ? AND username = ?;
SELECT id, username, is_admin FROM users WHERE id = ?;
```

不要只凭用户名或只凭 ID 进行高权限变更。

### 用户权限/资格状态表

| 字段/表 | 作用 | 管理路径 |
| --- | --- | --- |
| `users.is_admin` | 管理员权限 | `/admin` 或受控 SQL |
| `users.is_review_exempt` | 审核豁免 | 管理员接口/SQL |
| `users.slot_count` | 角色卡容量 | 管理员接口/SQL |
| `users.is_banned` | 封禁状态 | `/admin` |
| `crowd_review_inspectors` | 巡查使资格/状态 | 众查/管理员维护 |
| badges 相关表 | 徽章、前缀、展示资格 | 徽章脚本或管理员维护 |
| `data_cards.review_status` | 卡片审核状态 | 管理员/众查流程 |
| `data_cards.is_public` | 卡片公开状态 | 用户公开/管理员处理 |

## 9. 公开战报功能维护

### 已有能力

| 功能 | 路径/接口 |
| --- | --- |
| 公开战报展览 | `/arena-reports` |
| 公开战报接口 | `/api/arena/public-reports` |
| 公开战报统计 | `/api/arena/public-stats` |
| 连续战报打包上传 | `/arena-reports/upload` |
| 连续战报上传接口 | `/api/arena/continuous-bundle` |
| 用户自己的战报管理 | `/me` 战报面板 |
| 公开状态切换 | `/api/me/battle-reports/[generationId]/publication` |
| 用户删除自己的战报 | `DELETE /api/me/battle-reports/[generationId]` |

### 公开备注

字段：

```text
battle_report_generations.note
```

规则：

- 最多 500 字。
- 备注是公开展示内容。
- 如果战报公开，备注保存时会与战报正文一起进行屏蔽词/敏感内容检查。
- 公开列表和详情都展示备注。

### 上传人显示

公开战报列表、详情、个人战报面板会显示上传人。优先使用战报记录上的 `username`，缺失时显示未知用户。

### 删除战报

用户可删除自己上传的战报。删除逻辑清理：

- `battle_report_generations`
- `battle_report_generation_combatants`
- `large_objects` 记录
- R2 正文对象（尽力删除）

统计接口只读取当前仍存在的公开战报，所以删除后的战报不会继续计入统计。

### 连续战报打包上传

路径：

```text
/arena-reports/upload
```

逻辑：

- 从浏览器 IndexedDB 读取连续战报会话。
- 用户选择一个会话。
- 按章节顺序合并 Markdown。
- 填写公开标题和公开备注。
- 可选择上传后立即公开。
- 作为一条 `battle_report_generations` 记录保存。

限制：

- 最多 50 章。
- 总正文最多 400000 字符。
- 上传时执行屏蔽词/敏感词检查。

### 普通竞技场战报公开

曾修复过“只有完整竞技场战报支持公开展示”的误判。当前普通竞技场、流式竞技场、连续战报打包、旧 `generate-battle-story` 都应被公开战报识别为 arena record。

维护时注意同步这些位置：

- `app/api/arena/public-reports/handler.ts`
- `app/api/me/battle-reports/[generationId]/publication/handler.ts`
- `app/api/arena/public-stats/handler.ts`

### 战报渲染

公开战报详情优先复用：

- `BattleReportCard`
- `MarkdownBlock`
- `hydrateBattleReportCardFromGenerationRecord`

不要把 HTML 字符串直接塞页面。渲染应走现有组件，避免出现 `node="[object Object]"` 这类未正确渲染的结构暴露给用户。

## 11. CSS 不加载 / 页面白底文字排查

症状：

- 网站打开后只有白底文字。
- CSS 或 JS 静态资源加载失败。
- 点击后请求返回无效响应。

排查顺序：

1. 浏览器 DevTools Network 看 `/_next/static/*` 是否 200。
2. 确认当前访问地址是否被安全头视为允许的 LAN HTTP。
3. 检查 `MAHOSHOJO_ENABLE_HTTPS_SECURITY_HEADERS`。
4. 检查 `lib/security/browser-headers.ts` 是否包含当前 IP 段。
5. 本地生产启动前确认完整构建。
6. 尽量使用 HTTPS 暴露公网服务。

## 12. Resend 邮箱配置

### 最小步骤

1. 在 Resend 添加域名。
2. 到域名 DNS 管理后台添加 Resend 要求的 TXT / MX / DKIM 记录。
3. 等待 Resend 验证通过。
4. 在服务端环境变量设置：

```env
RESEND_API_KEY=...
```

5. 设置发件域名/地址相关配置。
6. 重启服务并测试找回密码/验证邮件。

### 没有域名怎么办

- Resend 生产发信通常需要验证域名。
- 没有域名时可以先只测试本地账号系统，或者使用不强制邮箱验证的模式。
- 不建议在公开站点长期关闭邮箱验证和反滥用措施。

## 13. 备份与回滚

### 做功能前备份

推荐至少做一种：

```powershell
git status --short
git diff > backups\before-change.patch
```

或者复制项目目录到备份目录。注意不要把 `node_modules`、`.next`、真实 `.env.local` 无意识打包传播。

### 回滚代码

如果是自己刚改的文件，优先使用 git diff 定位后手工反向 patch。不要随便执行：

```powershell
git reset --hard
```

原因：工作区可能有用户未提交改动。

### 回滚 D1

D1 的 ALTER 多数不可直接撤销。回滚策略：

- 新增列一般保留不用。
- 新增表可在确认无依赖后 DROP。
- 删除/修改数据前先导出或备份。
- 高权限用户状态变更必须先读后改、改后读回。

## 14. 验证清单

```powershell
pnpm lint

pnpm test
```

如果只改前端展示，至少执行：

```powershell
pnpm lint

```

如果改认证、管理员、数据库、公开/删除能力，额外确认：

- 服务端权限校验存在。
- same-origin mutation 检查存在。
- 不能自我降权/最后管理员保护。
- 数据库字段线上已迁移。
- 删除逻辑不会误删其他用户数据。
- 公开内容有敏感词/屏蔽词检查。
- 不泄露任何服务端密钥到前端。
